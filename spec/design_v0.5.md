本文回答三个问题：

1. 谁有最终提交权？
2. 什么才算一次操作成功？
3. 每类接入代码能保证什么？

这三个问题定下来之后，再按"一次操作怎么被许可、执行、核对、提交"重写主干。v0.4 的读取面、计算差异、快照恢复、文件合并都作为组件保留；现有实验也全部保留，用来检查新架构是否兑现了原来的行为。

## 1 为什么要改

v0.4 里，"这个改动该不该保护"在四个地方各算一遍（行号以 v0.4.0 为准）：

| 位置 | 判断依据 | 代码 |
|---|---|---|
| 接入层算保护清单 | 人碰过、被占用（问运行时），加上预留给别的 Agent 的（自己记） | `shared_session.py`：`protected()` |
| 应用里的代码再加 | Agent 上次看过之后变了的面（按指纹比）、人选中的对象 | `blender_side.py`：`run_agent` 第 762–771 行；Unity 的 `RunAgent` 同理 |
| 接入层逐个跳过 | 选中、预留：运行时不知道这两条规则 | `shared_session.py`：`run_agent` 第 343–348 行 |
| 运行时事后判断 | 版本号：过时、人碰过、被占用 | `runtime.py`：`_precheck`、`_finalize` |

顺序是先在应用里执行并恢复（第 287 行），之后才逐个问运行时（第 326–363 行）。这时运行时的拒绝只能改账本，改不了场景；写进账本的是"执行后"的内容（第 358 行），不管恢复有没有成功。给 Agent 的说明再由接入层自己拼（`_describe`）。

实验能全部通过，只是因为这几处算出来碰巧一样。Unity 删除受保护对象时第一次出现不一致：

- **场景**：叶子没了（Unity 接入代码恢复不了被删的对象）；
- **账本**：叶子还在，高度 2.2（运行时拒绝了删除）；
- **说明**：告诉 Agent"已恢复成人的版本"。

三份"事实"各自成立，违反 P1。

## 2 一次操作的生命周期

**谁有最终提交权：只有运行时。** 决定和动手分开：运行时决定，接入代码动手，接入层只传话。

```
Agent 提交（一段代码，或一次工具调用）
   │
   ▼
① 许可      运行时开一张许可单
   │
   ▼
② 执行      接入代码照单执行，交回实际状态
   │
   ▼
③ 核对      运行时逐个面比较"许可要求"和"实际状态"
   │
   ▼
④ 提交      账本 = 实际状态
   │
   ▼
⑤ 告知      给 Agent、给人的说明，只从账本生成
```

另外一直有一个**观察者**在跑：定时看应用，发现人的修改就记进运行时。人的修改不需要许可，看到就记（R5）。

### 2.1 许可单

每次操作一张，只由运行时开，内容是：

| 项 | 说明 |
|---|---|
| 可以改的面 | 其余都要保持 |
| 要保持的面，以及原因 | 人改过 / 人选中（选项开启时）/ 别的 Agent 在这个 Agent 上次看过之后改过 / 预留给别的 Agent |
| 不许删的对象 | 人碰过的对象（R6），以及它们的父对象、祖先对象（删父对象会连带删掉子对象） |
| 执行前的指纹 | 运行时以为的场景现状 |

选中、预留、每个 Agent 看过哪些版本，都搬进运行时管理，规则只在这里算（P9）。

**整次拒绝、根本不执行**的只有：步骤已被人认领、Agent 被暂停，以及有类型的工具调用直接针对不许动的对象（例如 `delete_object("Leaf_3")`）。任意脚本运行时无法事先知道它会做什么，只能执行后核对。

### 2.2 执行

接入代码照单执行，自己不做判断：

1. 核对场景和许可单上的指纹。不一致说明人刚改过：**不执行**，交回当前状态。观察者把人的修改记进运行时，运行时重开许可单，再试一次。
2. 给要保持的对象拍快照，给不许删的对象做备份（第 5 节）。
3. 执行 Agent 的代码或工具调用。
4. 按许可单恢复：要保持的面拷回原值，被删的对象从备份放回。
5. 交回执行前、执行后（恢复前）、最终的实际状态，以及每一项恢复是否成功。

### 2.3 核对：每个面归入一类

| 类别 | 条件 |
|---|---|
| 已生效 | 许可允许，Agent 的改动在 |
| 已保留 | 许可要求保持，最终状态和执行前一样 |
| **违规** | 许可要求保持，最终状态和执行前不一样（恢复失败，或者接入代码恢复不了这类改动） |
| 超出范围 | 改到了追踪范围以外的东西（R18、R19） |

### 2.4 结局

| 结局 | 含义 | 算成功吗 |
|---|---|---|
| `committed` | 没有违规；可能部分生效（有面被保留） | 是 |
| `refused` | 许可阶段就拒绝，没有执行 | 否，场景没变 |
| `replan` | 场景已变，没有执行，重开许可后再试 | 中间状态 |
| `error` | Agent 的代码出错；已生效的部分照实提交 | 否 |
| **`breach`** | 有违规的面 | **否** |

**成功** = 没有违规的面，并且账本和场景一致。

### 2.5 提交和告知

- 账本按**实际状态**提交，不按许可单上希望的结果。违规的面也照实记下：作者是这个 Agent，标"违规"。
- 告知只从账本生成：哪些生效、哪些被保留（带现在的值和它想改成的值）、它错过了什么（R22）。"你错过了什么"直接从账本历史里算：从这个 Agent 看过的版本到现在，每个版本是谁改的、改成了什么。

## 3 不变量

每次操作之后都能检查，测试和实验里每次都检查：

1. **账本 = 场景**：账本里每个面的指纹，和应用里实际的指纹一致。
2. **保持的就是保持的**：许可要求保持的面，要么确实没变，要么被记成违规。
3. **说的都是真的**：说明里的每一句话，都能在账本里找到对应的记录。

v0.4 的实时同步在每次同步后已经核对两边是否一致（`spec_v0.4.md` 9.4 第 5 步），这里推广到所有方式。这三条成立，README 的承诺就成了能自动检查的性质。

## 4 接入代码的契约与能力探测

每类接口的接入代码只实现 `spec_v0.4.md` 0.6 的五个通用动作。它能保证什么，**不手写**（P4），而是由运行时在连接时跑一套对所有应用都一样的自测探测出来：

1. 新建一个临时对象，读出它的面；
2. 改它的一个面，按面恢复，比较指纹；
3. 删掉它，尝试从备份恢复，比较指纹；
4. 在一次执行里连续改几处，看中途能不能被人的操作插进来（原子性）；
5. 清理临时对象。

探测结果就是这次连接的能力表。运行时开许可单时参考它：恢复不了的改动，有类型的调用就事先拒绝；任意脚本就只能执行后核对，核对出来是违规时如实报告。探测结果即使不准，每次操作后的核对（第 3 节）也能保证不说谎。

按现在的代码，预计探测结果是（2026-10-09 起 Blender 和模拟应用是实测的，见 13.6）：

| 能力 | Blender 方式一 | Unity 方式一 | 实时同步 | 文件兜底 |
|---|---|---|---|---|
| 一次执行是原子的 | ✔ 主线程上一次调用 | ✔ 一次 RunCommand | ✗ 两个应用，逐项核对 | ✗ |
| 恢复被改的面 | ✔ | ✔ | ✔ 人改过的不写入 | ✔ |
| 恢复被删的对象 | ✔ 从快照追加 | ✗（第 5 节） | ✔ 人那份不受影响 | ✔ |
| 场景外的改动 | 只能发现 | 只能发现 | 只能发现 | — |

## 5 恢复不了的改动：分四层处理（以 Unity 删除为例）

前一层拦不住的交给后一层，最后一层保证至少不说谎。

| 层 | 做法 | 管什么情况 | 能保证吗 |
|---|---|---|---|
| 1 执行前拒绝 | 许可单写"不许删"，有类型的 `delete_object` 直接拒绝 | 用小工具删除（要有 MCP 代理） | 能 |
| 2 删除时拦下 | 包装 Agent 的 C# 时，把 `DestroyImmediate` 换成运行时的版本：受保护的不删，并记下来；其余的改用 `Undo.DestroyObjectImmediate` 删，人可以 Ctrl+Z | 脚本里常规写法的删除 | 能被绕过（反射、菜单命令、其他写法） |
| 3 从隐藏备份重建 | 执行前用 `Object.Instantiate` 复制不许删的对象，设为 `HideFlags.HideAndDontSave`，记下父对象、兄弟顺序、启用状态，以及场景里哪些属性引用了它；执行后对象还在就删掉备份，不在就放回原处，再把引用重新指回来；运行时记一条编号映射（Unity 的编号用 `GetInstanceID()`，重建后会变，每个组件也一样） | 绕过了第 2 层的删除 | 大部分能；预制体关联、场景外的引用接不回来，记为"恢复不完全" |
| 4 如实报违规 | 结局 `breach`（第 6 节） | 以上都没兜住 | 保证不说谎 |

同样的分层适用于所有接入代码恢复不了的改动，例如脚本写了磁盘文件、改了别的场景：能事先拒绝的就拒绝，能恢复的就恢复，都不行就如实报告。

## 6 违规时怎么办

结局是 `breach` 时：

1. **账本照实记**，例如"Leaf_3 已被 Agent 删除（违规）"，和场景一致。
2. **提醒人**：哪个对象、哪里被改了，以及能不能用 Ctrl+Z 撤回（例如走了第 2 层的删除能撤，直接 `DestroyImmediate` 的不能）。
3. **暂停这个 Agent**（R17），等人处理。它接下来的步骤很可能依赖刚删掉的东西。默认暂停，可以配置为只提醒、不暂停。
4. **如实告诉 Agent**：例如"你删除了 Leaf_3，它是人改过的，无法自动恢复；你已被暂停，等人处理"。

| 模块 | v0.4 | v0.5 |
|---|---|---|
| 运行时 `runtime.py` | 账本和规则，但事后才被问 | 唯一做决定的：开许可单、核对、提交；管选中、预留、每个 Agent 看过的版本 |

| 说明 `changes.py`、`_describe` | 接入层自己拼 | 只从账本生成 |

**保留为组件**：读面和值（`records`、`object_values`，Unity 的 `Faces`、`Show`），差异描述（`changes.py`，改为从账本取数据），快照和恢复（`apply_faces`、`_put_in_place`），文件三方合并（`filemerge.py`），带核对的同步写入（`apply_sync`），`local_server.py`，以及全部实验。

**要删掉的**：接入代码里自己判断保护的部分（`blender_side.run_agent` 里根据 `known` 扩大保护集的那段、Unity 的对应部分），接入层里事后逐个 `submit` 的循环，接入层自己拼说明的部分。

## 8 三种方式走同一条流水线

| | ② 执行这一步换成 | ③ 核对 |
|---|---|---|
| 方式一：同一份 | 在应用里执行 Agent 的代码或工具调用 | 交回的实际状态 |
| 方式二：实时同步 | 把 Agent 那边的改动按许可写进人这边（带核对） | 写入后两边的实际状态 |
| 文件兜底 | 按许可合并两份文件 | 合并后重新解析的结果 |

许可、核对、提交、告知四步完全相同，规则只有一份。

## 9 一步一步的小工具与提示词

脚本是完整执行的，"部分生效"是执行后把不允许的部分改回来。这有两个弱点：恢复不了的改动（第 5 节），以及派生的改动（`spec_v0.4.md` 第 15 节第 22 条）。让 Agent 一步一步做能缓解这两点：

- **事先拒绝**：小工具的目标在执行前就知道，不许动的直接拒绝，不需要恢复。
- **派生改动少**：每一步之后 Agent 都看到哪些被保留，下一步基于现在的值。

做法是路线图第 1 项的 **MCP 代理**：Agent 连代理，不直接连应用的 MCP 服务器。

- 代理提供小工具：`set_property(对象, 面, 值)`、`create_object`、`delete_object`……由代理生成应用的脚本来实现。面本来就是自动读出来的，一个通用的 `set_property` 就能覆盖大部分情况，不违反 P4。
- 执行脚本的工具保留，作为复杂任务的兜底，走"执行后核对"。
- 提示词只简短说明规则和工具，用来减少冲突和无用功；安全不靠它（P2）。真实大模型实验里对比"有提示词"和"没有提示词"：两种情况下人的修改都应该被保住，区别只在冲突次数和浪费的步数。

一次工具调用就是一次操作，走第 2 节的同一条流水线。

## 11 实施顺序

每一步做完都跑全部测试和实验，有保护的那几行数字不能变差。

| 步 | 内容 | 验收 |
|---|---|---|
| 1 | 写不变量检查（第 3 节），并加一个复现 Unity 删除问题的测试（不需要 Unity：用一个"恢复不了删除"的假接入代码） | 新测试**失败**，说明不变量抓得到这个问题 |
| 2 | 许可单收进运行时；接入代码删掉自己判断的部分，只照单执行 | 实验 A、D 的数字和 v0.4 一样 |
| 3 | 按实际状态核对和提交；`breach` 结局、提醒人、暂停 Agent；说明只从账本生成 | 第 1 步的测试通过，结局是 `breach`，三份事实一致 |
| 4 | 能力探测；Unity 删除按整个对象判断；Unity 隐藏备份重建（第 5 节第 3 层） | Unity 自测：Agent 删掉人改过的对象后，对象回来，结局 `committed` |
| 5 | 实时同步、文件兜底接到同一条流水线 | 实验 B、文件兜底的数字和 v0.4 一样 |
| 6 | 标记的一键清除（P3） | 清除后文件里没有 `rightofway_*` |

MCP 代理和小工具（第 9 节）在这之后做。

### 11.1 第 1 步的结果（2026-10-03）

做了什么：

- `rightofway/invariants.py`：三条不变量的检查。I1 拿账本和场景比；I2、I3 针对一次 Agent 执行，用报告里新加的 `before`、`after_raw`、`after`、`plan`（应用侧实际用的保护集；Unity 不交回时由接入层按同样的规则推算）。v0.4 的说明文字由报告里的"已生效 / 没有生效"两项生成，I3 检查的就是这两项。
- `rightofway/fakeapp.py`：内存里的假应用，说和 Blender、Unity 接入代码相同的协议。`FakeApp(restore_deleted=False)` 和现在的 Unity 接入一样恢复不了被删的对象，不需要 Unity 就能复现问题。
- 实验 A、B（实时同步）、C、D 每一步之后都检查不变量，结果表新增"不变量违反"一列（涉及的对象数）。文件兜底还没接上。
- 新增实验 E（AI 删掉人刚改过的对象，就是那张时序图）和 `tests/test_invariants.py`。描述 v0.5 应有行为的测试标为 `xfail(strict=True)`：现在必须失败，修好后会提醒去掉标记。

发现：

| 情况 | 场景 | 账本 | 告诉 Agent 的 | 违反 |
|---|---|---|---|---|
| 模拟 Unity 接入，按面或按对象 | Leaf_3 没了 | Leaf_3 的位置还在（人的版本） | "Location 人改过，保留人的"，或"已恢复成人的版本" | I1、I2、I3 |
| Blender，按面 | Leaf_3 被整个恢复 | 一致 | "部分生效：Leaf_3（其余 101 个面已生效；Location 保留人的）" | I3 |
| Blender，按对象 | Leaf_3 被整个恢复 | 一致 | "没有生效（人改过，已恢复成人的版本）" | 无 |
| 实验 A、B、D 的所有有保护运行 | — | — | — | 无 |

第二行是这次新发现的：按面记录时，接入层把"删除对象"拆成每个面各提交一次，人改过的面被拒，其余的面被运行时接受。R6 的本意是人碰过的对象整个不能删。所以许可单里的"不许删"必须按整个对象（2.1），核对时删除也要按整个对象判断。

### 11.2 第 2 步的结果（2026-10-04）

做了什么：

- **运行时开许可单**（`Runtime.admit`）：要保持的单元和原因（人改过 / 人选中 / 别的 Agent 刚改过 / 预留给别的 Agent）。它和 `submit` 用同一组判断函数（`_claim_conflict`、`_target_conflict`），新测试 `test_permit_and_submit_agree` 把 32 种状态组合逐一对照：许可单要保持的，正好就是直接提交会被拒的。
- **搬进运行时的状态**：每个 Agent 看到的版本（`Runtime.seen`，`mark_seen`；Agent 自己提交的版本自动算看到过）、人选中的对象（`set_selection`，"选中即占用"是运行时的选项 `selection_occupies`）、预留（`reservations`，`close_permit` 发放和回收）。新增拒绝状态 `rejected_reserved`。
- **接入代码只照单执行**：`blender_side.run_agent`、Unity 的 `RunAgent`、`fakeapp` 删掉了自己按 `known` 扩大保护集、按选中保护的代码。执行前核对场景（每个对象的指纹，选项开启时还有选中状态）和许可单附上的一致；不一致就不执行，返回 `replan`，接入层把人的修改记进运行时后重开许可单（最多 3 次，之后报告"场景一直在变，没有执行"）。`known` 只剩一个用途：决定带回哪些面的值。
- **接入层**（`shared_session.py`）不再判断选中、预留，被拒的原因直接取自许可单。
- Unity 的自测不经过 Python 运行时，所以在自测的 C# 里模拟运行时开许可单。

### 11.3 第 3 步的结果（2026-10-04）

做了什么：

- **运行时按实际状态核对、记账**（`Runtime.settle`）：接入层把执行前、执行后（恢复前）、最终三份状态交给运行时，运行时逐个单元下结论（2.3）：已生效、保持（Agent 改到了、按许可单保持、场景里确实没变）、违规、被改回去（不在许可单里、应用却改回去了）、连带变化（Agent 没直接改、场景里却变了）。最终状态和账本不一样的单元一律按最终状态提交，所以结束后账本 = 场景。
- **删除按整个对象判断**：Agent 删除了有要保持部分的对象（`Permit.no_delete`），这个对象的全部单元都算要保持。应用恢复了 → 告诉 Agent"人改过的对象不能删除，已恢复"；没恢复 → 整个对象都是违规。
- **违规结局**（第 6 节）：账本照实记下（版本标 `breach`，"人碰过"标记保留），发出提醒人的事件，默认暂停这个 Agent（`pause_on_breach`）。被暂停的 Agent 开不出许可单，直接提交也被拒（`rejected_suspended`），直到人调用 `resume_agent`。
- **说明只从记账结果生成**：报告里的"已生效 / 没生效 / 违规"全部取自 `Settlement`；给人的提醒（`AgentReport.alert`）也是。
- 对照组保持原来的记账方式（模拟没有 RightOfWay），数字可以和以前比。
- 实验结果表加了"违规"一列；`evaluate` 把违规算进"人的修改被覆盖"（人的修改确实丢了），并单独列出"已如实报告"。

## 12 真实 AI 的写法：测量结果与设计（2026-10-04）

前面的实验里，AI 的脚本只精确地改几处。调研（`related_work.md` 2c）显示真实的 AI 不这样写：Blender 上是一次执行一大段代码（BlenderMCP 的 `execute_blender_code`、Blender 官方 MCP），研究系统每一轮重新生成整个程序（SceneCraft、LL3M、VIGA）；Unity 上是类型化工具，常用 `batch_execute` 一次发最多 25 条，不是事务（CoplayDev unity-mcp）。这一节先量这几种写法下会发生什么，再据此定"认回同一个对象"和"重叠时默认怎么处理"。

### 12.1 实验 H

四种写法，表达的是同一个计划（`experiments/scenario_tree.py` 的 `PLAN_*`，假应用的版本在 `scenario_fake.py`）：

| 写法 | 做法 | 对应的真实做法 |
|---|---|---|
| 精确修改 | 只改这一步想改的几处（原来实验里的脚本） | 少见 |
| 整体调整 | 遍历执行时场景里的所有物体，按类型统一设置位置、旋转、缩放、材质 | 一次一大段脚本 |
| 清空重建 | 先删掉场景里所有东西，再按自己的计划带着这次的调整重搭一遍 | 每轮重新生成整个程序 |
| 类型化批量命令 | 按自己上次看到的场景写出一条条 modify / create / delete，每批最多 25 条，不是事务 | Unity MCP 的 `batch_execute` |

在三种应用上跑：Blender（bpy 4.5，无界面）；模拟 Blender 接入（能恢复删除）；模拟 Unity 接入（恢复不了删除）。批量命令只在模拟应用上跑，Blender 的 AI 只能执行代码。

两种测量：

1. **原来的故事**：场景 A（一个 AI + 人）、D（两个 AI + 人）、E（AI 删掉人改过的对象），每种写法跑一遍。
2. **逐一试人的单个修改**（`--sweep`）：AI 布置好场景之后，人改一处，AI 不知道，按原计划执行场景 A 的第 2 步。人的修改逐一试：Blender 是 11 个对象各自的移动、旋转、缩放、删除，加上 3 种共用材质的改色；模拟应用是每个对象的每个面，加上删除。

为此新增的代码：

- 假应用有了对象类型和父对象（父对象是一个面，值是父对象的编号：删掉再新建的父对象是另一个编号）。
- **类型化命令的预检查**：`SharedSession.run_commands` 每一批先开许可单，用 `Permit.screen` 检查每条命令：改到要保持的面的，去掉这些面再执行；整条都要保持的、删除不许删的对象的，不执行。其余交给应用执行，之后照常核对、记账（`Runtime.settle` 新增参数，执行前拒掉的单元算作"Agent 想改、按许可单保持"，同样要核对场景里确实没变）。
- **认回同一个对象**的原型（12.4），`Runtime(reidentify=True)`，默认关。

### 12.2 结果

**人改一处，撞上 AI 这一步的概率**（`--sweep`；"撞上"指 AI 这一步改到了人刚改的那个面）：

| 写法 | Blender | 模拟应用 | 撞上之后（不认回） | 撞上之后（认回） |
|---|---|---|---|---|
| 精确修改 | 11/36（31%） | 14/49（29%） | 全部保住 | 全部保住 |
| 整体调整 | 30/36（83%） | 37/49（76%） | 全部保住 | 全部保住 |
| 清空重建 | 36/36（100%） | 49/49（100%） | **违规**：Blender 36/36，模拟 Blender 接入 20/49，模拟 Unity 接入 49/49；Blender 里共多出 47 个重复对象 | 全部保住，没有重复对象 |
| 类型化批量命令 | — | 37/49（76%） | 全部保住：执行前拒掉，或者去掉冲突的面 | 同左 |

按对象算（AI 这一步改到了人刚改的那个对象的任何一个面），四种写法都在 83%–100%。

**人删掉一个对象**（11 种），AI 这一步：

| 写法 | 把它补回来了 | 脚本出错 / 命令失败 |
|---|---|---|
| 精确修改 | 3（三块石头：脚本"缺了就补"） | 1（删掉的是树干，脚本中途出错，前面的修改已生效） |
| 整体调整 | 3 | 0 |
| 清空重建 | 11 | 0 |
| 类型化批量命令 | 0 | 10（命令按旧场景写，目标不在了，这一条失败，其余照常） |

**原来的故事**（`habits.csv`，节选）：

| 场景 | 写法 | 应用 | 不认回 | 认回 |
|---|---|---|---|---|
| A | 清空重建 | Blender | 人改过的 Leaf_3 恢复后改名为 Leaf_3.001，和 AI 新建的 Leaf_3 并存，父对象断开；违规，AI 被暂停 | 只有一个 Leaf_3：人挪的高度、AI 的秋天颜色、仍挂在树干上 |
| D | 清空重建 | Blender | 材质 AI 按旧印象重建，把布局 AI 刚建好的 10 个对象删掉又恢复：11 个重复对象，11 处违规，两个 AI 都被暂停 | 0 重复、0 违规 |
| E | 清空重建 | Blender | Leaf_3 恢复了，但原来的树干被重建，父对象断开：违规 | 父对象对上，0 违规 |
| A、E | 清空重建 | 模拟 Unity 接入 | 恢复不了删除：2 处、1 处违规 | 各剩 1 处：人新建的 Cube、AI 不要的 Leaf_3 被删了，AI 没有新建同名的，认回帮不上 |
| A、D、E | 类型化批量命令 | 模拟 Unity 接入 | 0 违规：删除在执行前就被拒了 | 同左 |
| 全部 42 行、381 次逐一试 | | | 三条不变量全部成立 | 同左 |

实验 A–F 原来的 19 行数字和第 3 步完全相同。

### 12.3 结论

1. **重叠是常态。** 按真实的写法，人在 AI 这一步之前改的一处，有 76%–100% 的概率被这一步改到；就算是精确修改也有约 30%。按对象算是 83%–100%。
2. **所以"撞上就整步退回、让 AI 重新生成"不能当默认。** 人在场时，AI 大部分步骤都会被整步退回；每次重新生成都是一整段大脚本、一次完整的模型调用；人一直在改，AI 就可能一直提交不了。部分生效在全部撞上的情况里保住了人的修改，AI 其余的改动照常生效。
3. **清空重建破坏对象的身份。** 运行时看到的是"删了 N 个、新建了 N 个"：人改过的对象被恢复，和 AI 新建的同名对象并存，父对象断开，结局全是违规，AI 被暂停。系统如实报告了（不变量全部成立），但没法用：人只要改了任何一处，清空重建的 AI 就停下来。
4. **类型化命令能在执行前拦下冲突**，应用恢复不了的删除也不会发生；按旧场景写的命令会失败，而不是把人删掉的东西补回来。
5. **AI 会把人删掉的东西补回来**：代码写法 11 种删除里补回 3–11 种。现在只能提示（R6 不管新建）。

### 12.4 设计：认回同一个对象（2026-10-09 加固后默认打开，13.2）

**规则**（运行时写在许可单里，接入代码只照做，P9）：一次执行里，被删掉的对象和新建的对象，**名字相同（先比完整名字，再比去掉 `.001` 后缀的）、类型相同**的，一对一配上，新对象接过旧对象的编号，当作同一个对象被修改。

- 配上之后不用新的恢复逻辑：现有的按面保护照常起作用，人改过的面从快照拷到新对象上。
- 引用按编号记录：新叶子的父对象是新树干，新树干接过了旧树干的编号，所以父对象这个面没变；恢复出来的对象（例如 E 里 AI 不要、没有新建的 Leaf_3）在快照里指向旧树干，也按编号找到新树干。
- 只用名字和类型，每个应用都有（P4）。
- 不改应用（P3）：Blender 是把 `rightofway_id` 盖到新对象上；假应用是换编号。
- **Unity**：编号是 `GetInstanceID()`，没法交给新对象。接入代码按同一个规则配对，把人改过的面从执行前的快照写到新对象上（`EditorJsonUtility.FromJsonOverwrite`；改属性 Unity 做得到，做不到的只是把删掉的对象放回原处），运行时记一条编号映射。和第 14 节第 1 条（`GlobalObjectId`）一起实测。
- **核对**：运行时手里有执行前和执行后两份记录，可以自己重算配对，和接入代码交回的不一致就是违规（原型还没做这一步）。
- **会不会认错**：AI 删掉一个对象、又新建了同名同类型、但它心里是"另一个东西"时，会被当成同一个对象。后果是人改过的面套到新对象上（例如人摆的位置）。这符合人优先；其余的面都是 AI 的。

原型的结果见 12.2：所有清空重建的情况都变成 0 重复、0 违规；模拟 Unity 接入剩下的违规都是"删了没有新建"的纯删除，归第 5 节的分层处理。

**建议**：默认打开。打开之前先做两件事：Unity 接入代码实现、运行时核对配对。

### 12.5 设计：人删掉的，不让 AI 悄悄补回来（2026-10-09 已实现，13.3）

同一个配对规则用在人删掉的对象上：AI 新建的对象和人删掉的某个对象同名同类型，而这个 AI **没看到**那次删除（它看到的版本早于人删除的那个版本），就是按旧印象改了人碰过的东西（R4 + R6）：

- 许可单多一项"不许重建"：人删掉、这个 AI 还没看到的对象的名字和类型。
- 接入代码把配上的新对象删掉。删掉 AI 刚新建的对象每个接入代码都做得到，包括 Unity。
- 告诉 AI："人删掉了 Rock_2，你还没看到这次删除；没有补回来。"
- AI 看到了删除还新建同名的：算有意的，照常新建（新编号，不认回）。

需要的程度：12.2 里代码写法补回了 3–11 种删除。

### 12.6 设计：祖先不许删（2026-10-09 已实现，13.3）

`Permit.no_delete` 现在只有"有要保持单元的对象"本身。要加上它们的祖先：记录里本来就有 `parent`，通用（P4）。H 的场景里被删的祖先都被重建了，认回就够；纯删除祖先时（AI 不要整棵树），Blender 里子对象的父对象会断开，Unity 里子对象会被连带删掉，两种都是违规。祖先不许删之后，树干被恢复，人改过的叶子不受影响。

### 12.7 默认怎么处理重叠

1. **部分生效**（现在的行为，默认）：不冲突的照常生效；冲突的面保留人的（或先到的 AI 的）。
2. **针对性重新生成**：说明里列出哪些没生效、现在的值、它想改成的值（R22，已有）。AI 只需要重新考虑这些面，不用重做整步。不会死循环：每一步不冲突的部分都提交了，再撞上的面同样保留人的。
3. **意图冲突**：部分生效后的组合可能两边都没想要。例如 E 的整体调整：AI 把 4 片叶子均匀排开，人的 Leaf_3 还在原处，挤在一起。运行时不知道意图，不判断；说明告诉 AI 哪些没生效，由 AI 下一步自己调整。可以加一个选项：AI 标明"这一步要么全做、要么不做"，撞上就整步不执行、让它重新生成。这只是选项，不是默认（12.3 第 2 条）。
4. **类型化命令**：执行前预检查，能拒的不执行；**代码**：执行后核对。两者走同一张许可单。

### 12.8 预检查和 P4

预检查要知道一条命令改哪个对象、哪些面。对象好说：CRUD 形式的工具都有目标参数。参数到面的对应却是每个工具不一样的（例如 `position` 对应 Unity 的 `m_LocalPosition`），手写就违反 P4。分两步：

1. **现在**：只在对象这一级预检查，不需要知道面：删除不许删的对象、整个对象都要保持的，执行前拒绝。面这一级照旧执行后恢复，改属性每个接入代码都能恢复。
2. **能力探测**（第 4 节，第 4 步）：每个工具在临时对象上调用一次，看哪些面变了，就得到参数到面的对应，不用手写。

### 12.9 重新评估"暂存"

暂存 = AI 在副本上执行，运行时只把允许的改动搬到真场景（曾想作为 P10）。

- 类型化命令的预检查就是一种暂存（先决定、再执行），12.2 里效果很好。
- 代码执行的暂存不当默认：Blender 的材质、网格是全局数据块，在场景副本上执行照样改到真场景用的数据（H 的脚本都改了共用材质）；复制整个文件代价高；Unity 的资源也是共享的。
- 结论：不加 P10。留作选项，给能便宜地开沙盒的应用。

### 12.10 建议的下一步

（2026-10-09：第 1–4 项已做，第 5 项做了能力探测，见第 13 节。Unity 那一侧还没做。）

1. 认回同一个对象：Unity 接入代码实现、运行时核对配对，然后默认打开。
2. 人删掉的不让 AI 悄悄补回来（12.5）。
3. 祖先不许删（12.6）。
4. 类型化命令的对象级预检查接到 MCP 代理（第 9 节、12.8）。
5. 第 4 步（能力探测、Unity 隐藏备份）照旧：纯删除仍然要靠它。

## 13 按调研加固（2026-10-09）

调研（`prior_art_solutions.md`）建议的六项按顺序做了；第 7 项（Agent 自己声明意图）、第 8 项（向 MCP 标准提议）不写代码。

### 13.1 共用数据块是单独的单元（第 1 项）

- 方式一的 Blender 接入里，对象直接引用的数据块（材质、网格、灯光数据……）各自盖章、各自是一个单元，有自己的面；对象的面里只记"引用了哪个"（`data:编号`）。哪些属性是引用、数据块有哪些面，都从 RNA 读出（P4）。
- 删除：数据块从文件里删掉才算删除；没有对象用了仍然追踪。
- 恢复写回同一个数据块：只有部分面要保持，就按面复制；整个要保持（或者按面复制没成功），就让所有使用者改指向快照里的副本，副本接过编号和名字。快照追加时带进来的同编号副本，一律指回场景里现在的那一个。
- 实时同步、文件兜底仍按对象（第 11 节第 5 步）。
- 结果：人改一次共用材质的颜色，只记一次，记在材质上；AI 再改同一个材质时，人的颜色保留，5 片叶子还用同一个材质，没有 `.001`（`spec_v0.4.md` 第 15 节第 25 条）。实验 H 的"数据块分叉"在所有有保护的运行里是 0。

### 13.2 认回同一个对象：加固，默认打开（第 2 项）

规则在 `rightofway/identity.py`，运行时和接入代码用同一份（发进 Blender 时，bridge 把它的源码放在 `blender_side.py` 前面）：

- **同一个父对象下从上往下配对**：先比完整名字，再比去掉重名后缀的名字，最后才不管父对象、只要名字全局唯一；类型必须相同；一对一，有歧义就不配。配上的等级（exact、suffix、global）就是置信等级，记在运行时的认回记录里（`Runtime.identity_log`）。
- **重名后缀不手写**：连接时的自测（13.6）让应用新建两个同名的东西，看第二个叫什么。Blender 学出 `\.\d+`；Unity 和允许重名的模拟应用学不出后缀，只比完整名字。
- **三种"旧的"**，同一条规则：
  - gone：这次执行里 Agent 删掉的。数据块也算：执行前有对象用、执行后没人用了的，和新建的同类型数据块配对；没人用的旧数据块随后删掉，不再占着名字。
  - rebind：Agent 之前想删、因为人改过而保留下来的（"孤儿"）。清空和重建分两次执行时，第二次新建的认成它。Agent 后来又去改它，或者它不再受保护，就不再认。
  - tomb：人删掉、这个 Agent 还没看到的（12.5 的墓碑，见 13.3）。
- 去掉后缀才配上的，名字还给它（`Leaf_3.001` → `Leaf_3`）：后缀只是因为和旧的重名。
- **编号能转交的**（Blender：把 `rightofway_id` 盖到新对象上）直接转交；**不能转交的**（Unity 的 `GetInstanceID`，模拟应用 `transfer_ids=False`）记一条"应用编号 → 运行时编号"的映射，会话保存、每次调用都带上，接入代码报给运行时的一律是运行时编号。这就是调研里说的"改名表"。
- **运行时核对**：接入代码交回配对和新对象原来的样子；运行时只用执行前、执行后（恢复前）的记录，按同一条规则重算一遍（`identity.verify`），必须完全一样。不一致的照实记下、提醒人（`Settlement.identity_errors`），不暂停 Agent，因为这是接入代码的问题。
- 告诉 Agent："你删掉又新建的这些对象，按同一个对象处理（编号不变，人改过的部分照样保留）：……Leaf_3_mesh（去掉重名后缀后同名）"。
- `Runtime(reidentify=True)` 现在是默认值。实验 H 用 `--no-reidentify` 做对照。

### 13.3 人删掉的不补回来，祖先不许删

- **墓碑**（12.5）：许可单的 `no_recreate` 列出人删掉的对象：这个 Agent 看到过它还在，但还没看到它被删。Agent 新建了同一个（同一条配对规则），接入代码在恢复之后把它删掉，连同只给它用、也是这次新建的数据块；运行时记为保持（`kept`，`recreate`）。告诉 Agent："人删掉了这些对象，你还没看到这次删除；你新建的同名对象已删掉，没有补回来：Rock_2"。看到过删除之后再新建，照常新建。
- **祖先不许删**（12.6）：许可单的 `keep_alive` 是要保持的对象的祖先，从账本里每个单元记的 `parent` 往上找（P4）。被删了就整个放回，面照样可以改；类型化的删除命令在执行前就拒。告诉 Agent："没有生效（已恢复；下面有人改过的对象，不能删除）：Trunk"。
- 这两条和 rebind 一起，让"这一次清空、下一次重建"也能用：第一次删不掉的 Trunk、Leaf_3 留下，人挪的 Leaf_3 还挂在 Trunk 上；第二次新建的 `Trunk.001`、`Leaf_3.001` 认成它们，不出现两份，名字也还原（`tests/test_identity.py`，Blender 和模拟应用都测了）。

### 13.4 告知：失效的事实、新的目标、循环检测（第 3 项）

- 每个没生效的面一条记录，参照 K8s 的 409：面、所有者、现在的值、它想改成的值（`AgentReport.conflicts`）。
- 说明里加一段"以现在的值为准（请当作新的目标，写进你之后的计划；下次重建或调整时直接用这些值）"：人定的值、删不掉的对象、人删掉的对象（RIR 的"待重新核实"、Flux 的 Adopt）。这一步里其余已生效的修改，如果是按这些部分原来的值算出来的，请按新的值重新核对。
- **派生改动**：Agent 新建的数据块是已有数据块的副本（X → X.001，用探测出的后缀判断），或者人改过的数据块少了使用者（换了材质，人在它上面的修改在这些对象上看不到了），都告诉 Agent。只告知，不拦。
- **循环检测**：从账本算，同一个单元在这个 Agent 最近 5 次执行里被保持了 3 次（`Runtime(loop_repeat, loop_window)`），告诉 Agent 不要再改，并提醒人一次。不暂停：这是告知，不是安全手段。
- **结构化结果**：`SharedSession.payload(report)`；`SharedSession.is_error(report)` 决定 MCP 的 `isError`。

### 13.5 MCP 代理（第 4 项）

`rightofway/proxy`，用法：`python -m rightofway.proxy -- uvx blender-mcp`（"--" 后面是原来启动应用 MCP 服务器的命令）。

- 运行时自己的调用（自测、列对象、执行……）经过上游的执行代码工具发进应用（`MCPBridge`），接入代码和实验用的是同一份；也可以 `--bridge socket` 直接连插件。
- **执行代码的工具**（自动找：有一个必填的字符串参数，参数名像代码）→ `run_agent`：原子地执行、恢复、核对。
- **上游的其他工具**：调用参数里出现的对象名，就是它要动的对象（不为每个工具手写映射）。按对象预检查（12.8 第 1 步）：整个对象都要保持的，不执行；接入代码事后恢复不了的（能力表里没有 begin/finish，或者恢复不了删除、而这个工具可能删除），不执行。其余的包在接入代码的 `begin_agent` 和 `finish_agent` 之间：核对、快照 → 调用上游 → 认回、恢复、核对。上游标为只读的工具，先告诉 AI 它错过了什么（注解不可信，只用来分流，调用后照样核对）。这条路不是原子的：两次调用之间应用里的变化都算 Agent 的。
- **代理自己的小工具**（第 9 节）：`rightofway_set_property`、`rightofway_create_object`、`rightofway_delete_object` 编成应用的脚本（Blender：`rightofway/blender/commands.py`，按 RNA 设置属性，引用按名字找），按面预检查后原子地执行，不需要恢复；`rightofway_observe` 告诉 AI 它错过了什么、现在哪些不能改。
- **结果**：说明放在 content 里；结构化结果放在 `_meta.rightofway`；有没生效、被拒、违规的部分时 `isError=true`。上游工具的 `outputSchema` 去掉，因为被拒、被包起来的调用给不出那种结构化结果。
- **给人的提醒**（违规、反复改、认回不一致）写进日志；接入代码支持的话也显示在应用里（Blender：`notify`，在界面里弹出提示）。
- **测试**：内存里的假上游（`rightofway/proxy/fake_upstream.py`）；两跳标准输入输出（AI 客户端 → 代理 → 假上游）；真的 BlenderMCP 服务器（mcp-for-blender 2.1.9）加 bpy 冒充的插件。为此 `local_server` 改成和插件一样：一个连接上可以连续发多条命令，可以同时有多个连接，命令都在主线程上执行。实验 P。
- 没做：等人释放对象时挂起调用（MCP Tasks）；Unity 的代理接入（Unity 接入代码要先指定实验场景）。

### 13.6 能力探测（第 5 项的一部分）

接入代码的 `probe` 在连接时测出能力表，不手写（第 4 节，P4）：

- 重名后缀（13.2）；
- 在一个临时场景里（模拟应用：一份临时的应用），用和平时完全一样的 `run_agent`、`begin_agent`、`finish_agent` 试三次：改掉的面能不能按面恢复；删掉的对象能不能恢复；两次调用之间的修改能不能恢复。临时的东西最后都删掉。

| 能力 | Blender | 模拟 Blender 接入 | 模拟 Unity 接入 | Unity |
|---|---|---|---|---|
| 按面恢复 | ✔ 测出 | ✔ 测出 | ✔ 测出 | ✔ 声明，未实测 |
| 恢复删除 | ✔ | ✔ | ✗ | ✗ 声明 |
| 包住不透明的工具调用（begin/finish） | ✔ | ✔ | ✔ | ✗ |
| 认回同一个对象 | ✔ 转交编号 | ✔ 转交编号 | ✔ 编号映射 | ✗ 还没实现 |
| 重名后缀 | `.001` | `.001` | 无 | 无 |

运行时用它决定许可单里写不写认回规则（`Runtime.identity_rule`），以及代理里哪些调用执行前就拒（13.5）。没做的：按工具测"它会改哪些面"。自动调用未知的工具可能有外部副作用（BlenderMCP 的下载资源、生成模型要扣费），只能由人逐个开启。Unity 的隐藏备份恢复（第 5 节第 3 层）也还没做。

### 13.7 影子执行（试验，第 6 项）

`experiments/exp_s_shadow.py`：AI 的脚本先在另一个 Blender（影子）里执行，带认回，不用恢复；再经实时同步的写入路径，只把允许的改动写进人的场景。实验 A 的第 2 步，两个 bpy 进程：

| 写法 | 直接执行 | 影子执行（前同步 + 执行 + 后同步） |
|---|---|---|
| 精确修改 | 0.26 秒 | 1.23 秒（0.37 + 0.19 + 0.66） |
| 整体调整 | 0.25 秒 | 1.25 秒 |
| 清空重建 | 0.35 秒 | 1.35 秒 |

六次运行的结局都一样：人的修改 0 处被覆盖，AI 的修改 0 处丢失，0 个重复对象，0 处数据块分叉，账本 = 人的场景。把人的修改换成改共用材质的颜色，也一样。

影子执行的好处是人的场景从来不会出现不允许的改动，不需要事后恢复。代价是这个小场景里每步多 1 秒左右（4–5 倍，主要在两次同步的导出和追加），而且不是原子的，靠写入前核对：同步时人刚好又改了的，跳过。实时同步还是按对象搬运，数据块不是单独的单元。

**结论**：Blender 不需要它（直接执行能恢复任何改动）。留给恢复不了的应用，或者人不想在自己的场景里看到一闪而过的改动的情况。

### 13.8 结果

`run_all`（无界面）：实验 A、B、D、E、文件兜底、P 全部通过，各列数字和第 3 步相同；只有"AI 不先看提示"那一行的"被删对象被重建"从 1 变成 0（补回被拦下）。实验 C、Unity 的 E 没有 Unity，跳过。

| 重复对象、数据块分叉 | 0 | 0 |

对照（`--no-reidentify`）：Blender 的清空重建 A 有 2 处违规、2 个重复对象（恢复出来的 Trunk、Leaf_3 的名字被 AI 新建的占了，只能叫 `.001`），D 有 12 处；模拟 Unity 接入 A 有 3 处，D 有 12 处。

### 13.9 还没做

- Unity 接入：认回、begin/finish、notify、能力实测、`GlobalObjectId` / `GetEntityId`、隐藏备份恢复。`probe` 如实报告这些都没有。
- 恢复不了删除的应用里，被 Agent 删掉的人改过的对象，之后的执行不会认回：人的值在应用里已经没了，要等隐藏备份。
- 撤销一次认回（"这不是同一个"）。认回记录可以查看，还不能撤。
- 按工具测效果（13.6）；代理里不透明的工具调用不是原子的；MCP Tasks。
- 意图冲突、派生改动只告知，不自动处理。

## 14 待定

1. **Unity 的编号**：`GetInstanceID()` 在重新加载场景后会变，重建对象后也会变。改用 `GlobalObjectId` 能跨重新加载保持不变，也不需要往文件里写东西，但还没保存过的新对象可能拿不到稳定的值，需要实测。
2. **违规时默认暂停**是否太严：等真实大模型实验后再看。
3. **第 2 层（删除时拦下）要不要做**：成本低，但能被绕过。有了第 3 层之后，它的主要价值是让 Agent 的普通删除也能用 Ctrl+Z 撤回。
