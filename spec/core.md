以前规则写了两遍：3D 一套（`runtime.py` 加 `shared_session.py`），代码一套（`code/ledger.py` 加 `hooks.py`），规则相同，代码、数据结构和叫法各是一套。现在只有一份核心，两边都调用它（P9）。核心只认识**单元**：有编号、有指纹、值能写成文字。它不知道这个单元是一个属性、一行，还是一个单元格。

## 1 统一术语

规范和代码里只用这一套词。给人和 AI 看的话，仍然用媒介自己的说法（"第 2 行"、"Leaf_3 的位置"）。

| 统一的词 | 意思 | 3D 原来的叫法 | 文本原来的叫法 |
|---|---|---|---|
| 单元 | 核心判断、记账的最小单位 | 面（对象的一个属性） | 行 |
| 容器 | 单元所在的地方；按编号的、按位置的两种（第 2 节） | 场景 | 文件 |
| 标记 | 单元最后一次被谁改成现在这样，以及第几版 | 版本记录 | 每行的标记 |
| 指纹 | 由内容算出的短字符串，内容不变指纹就不变 | 每个面的指纹 | 每个文件的指纹，变了再逐行对比 |
| 墓碑 | 删掉的单元（或整个对象、文件）留下的记号：谁删的 | 被删的对象 | 删除点、被删的文件 |
| 许可单 | 一次 AI 执行之前，核心开出的"哪些要保持、为什么" | 许可单 | 待结算 |
| 身份跟踪 | 新旧两份里哪个单元是哪个 | 认回 | 标记跟着行走 |
| 归人（hold） | 人或来源不明改过、还没交还 | 人碰过（`human_touched`） | 人和来源不明的标记，没交还的 |

意思不变的词：**基线**（没人改过的样子）、**来源不明**（说不准是谁做的，`external:<来源>`）、**违规**（要保持的单元实际被改了）、**交还**（人明确允许 AI 再改）、**视图**（某个 AI 上次看到的样子）。

作者有五类：基线、人、来源不明、别的 AI、git（人做的版本控制操作，例如切分支、拉取，带来的变化）。

## 2 单元和容器

**按编号的容器**（3D 的面，以后的 Excel 单元格）：单元有稳定的编号，按编号查。编号写成"对象编号#面"，一个应用对象的几个面是几个单元；删除和新建按整个对象算。墓碑落在编号上。删了又建的同一个东西靠**认回**接上旧编号：同一个父对象下名字（去掉应用自动加的重名后缀后）和类型都一样，一对一，有歧义就不配（`core/identity.py`，应用侧的接入代码用同一份源码）。认回是推断，可以撤销（"不是同一个"）。

**按位置的容器**（文本的行，以后的字符）：单元没有编号，按位置排。应用侧交来新旧内容的对应关系（和 difflib 的 `get_opcodes` 一样的五元组），核心据此移动标记：没变的单元带着原来的标记，新写出来的带上这次的标记，删掉的地方在两个位置之间留墓碑，整个容器删掉是位置 0 的墓碑。核心不知道单元是什么：比较两个单元是否相同、单元的文字，都由应用侧给。粒度由应用侧决定：代码按行；一致性测试里有一个单元是字符的玩具容器。

两种容器的判断完全一样（第 3 节）。账本只记有作者的单元：没人改过的是基线，不建记录，版本号缺省为 0。"全部算人的"（`initial_owner="human"`）这类情况用规则表示（基线归人），不逐个建记录。

## 3 判断表

单元和墓碑都用这张表（`rules.judge`）。先看这个单元现在归不归人，再看它最后是谁改的：

| 这个单元 | 这个 AI 能不能改 |
|---|---|
| 归人：人或来源不明改过、还没交还 | 不能，直到人交还 |
| 没人改过（基线），或者已经交还 | 能 |
| 最后是它自己改的 | 能 |
| 最后是别的 AI 或 git 改的 | 先看过这一版，才能改 |

- **归人和"最后是谁改的"分开记。** AI 违规改了归人的单元（第 5.3 节），账本照实记这个 AI 改的，但单元仍然归人。
- **墓碑看的是删掉它的是谁**（`rules.judge_tombstone`）：人或来源不明删的，人交还之前不能补回；它自己删的能；别的 AI、git 删的，先看过这次删除。AI 看没看到这次删除都一样："知道你删了"不等于"你允许它建回来"。
- **"看过"**：按编号的容器里，AI 每次看场景、每次执行完，记下那一刻（之后用到时从单元的历史里算出它看到的是第几版）；按位置的容器里，AI 读一个容器时记下容器的版本。
- **交还**：人在应用里点按钮、在对话里写命令（`交还 路径:起-止`）、或者提交（人的提交算交还提交进去的部分；AI 自己的提交不算）。交还是人的决定，马上落盘。

**暂时不能改的情况**（`rules.temporary`，按这个顺序报告原因）：

1. 人正选中着（选项："选中就算在改"，默认关）；
2. 预留给了另一个 AI：两个 AI 冲突后，被拒的那个得到一段预留（默认 30 秒），期间别的 AI 不能改这些单元，它下一次执行结束时预留就用完了；
3. 人正在改（占用），直到人交还。

**总闸**（`rules.gate`）：人暂停了全部 AI、有一次执行的结果还没查清、这个 AI 违规（或可能违规）后被暂停——什么都不放行。

**意图层的出口**（`rules.tighten`，这次不实现意图层）：许可单开出之后可以交给一个可选的层，它只能多要求保持一些单元，不能少，原来要保持的原因也不能改。关掉这一层（`tighten=None`），保护照样成立。

**只有人能改的单元**（例如 RightOfWay 自己的配置）：AI 任何改动都算碰到（`KEEP_LOCKED`），人永远不交还。

## 4 谁做的

AI 的执行之外看到的变化都是人的——除了下面几种（`rules.observed_author`）：

- 说不准是谁做的，记为来源不明，和人的修改一样保护：结果没查清的那次执行前后（`external:unattributed`）、RightOfWay 没运行期间（`external:offline`）、应用重新打开时（`external:reopened`）、增量观察漏掉、全量核对时才发现的（`external:missed`）；
- 变成了人的版本控制参照里的样子（HEAD 变了、内容和新的 HEAD 一样）：记为 git，和别的 AI 一样只防按旧印象改；
- 有一次不能原子执行的执行还开着时，它范围里的变化先不记在谁名下，等它结算（第 5.4 节）。

## 5 一次操作

```
准入（总闸）→ 开许可单 → 执行（应用侧做）→ 结算（逐个单元归类）→ 记账 → 说明
```

### 5.1 许可单

只由核心开：每个单元先过暂时不能改的情况，再过判断表；结果是要保持的单元和原因（人改过 `human`、人选中 `selected`、别的 AI 刚改过 `other_agent`、预留给别的 AI `reserved`），然后交给可选的收紧层。按编号的容器还有：不许删的对象（有任何一个单元要保持的对象整个不许删，以及它们的祖先：删父对象会连带坏掉人改过的子对象）、墓碑（不许补回的对象）、认回规则、可以重新绑定的旧对象（AI 之前想删、因为人改过而保留下来的）。

**生命周期**（每张正好结束一次，第二次结束直接报错）：

```
开出 issued → 已发出 dispatched → 已结算 settled（照实际状态记账）
                                → 已关闭 closed（没有执行：场景变了要重开、执行前就拒、或者查清了根本没执行）
                                → 结果未知 in_doubt → 已结算 / 已关闭 / 来源不明 unattributed（查不回来）
准入没过：拒绝 refused
```

- 发出之前，结果未知的记录已经落盘；
- 应用侧执行前先记"开始了"，按许可单编号记结果，同一张许可单只执行一次；
- 有一张许可单结果未知时，总闸不放行任何 AI，观察也不把差异算成人的。

### 5.2 执行之前就知道会改什么时

能事先算出结果的执行（按字符串替换的编辑、整份写入、类型化的命令）先按结果核对：

- 一次执行里的几个单元互相关联（例如一次编辑改名）：碰到不能改的就**整次拒绝**，一个单元都不改；
- 各自独立（例如一条命令设的几个属性）：去掉不能改的，其余照常（`rules.refuse_whole` 的 `separable`）。

事先算不出、但执行了一定会改的：容器里有对它不能改的部分，就整次拒绝。不知道会改哪些单元的工具调用：整个对象都要保持的，或者应用侧事后恢复不了的（不能把调用包在快照和恢复之间、恢复不了删除而这个调用可能删除），执行前就拒（`rules.opaque_blocked`）。

### 5.3 结算：每个单元归一类

按应用侧交回的执行前、执行后（恢复前）、最终三份实际状态，只看实际状态，不看许可单希望的结果：

| 类别 | 条件 |
|---|---|
| 已生效 applied | 可以改，AI 改了，最终就是它改成的样子 |
| 新建 created | AI 新建的 |
| 已保留 kept | 要保持，最终和执行前一样（恢复了、执行前就拒了、或者 AI 补回的墓碑被删掉了） |
| **违规 breach** | 要保持，最终和执行前不一样（恢复失败，或者应用侧恢复不了这类改动） |
| 改回去了 reverted | 不用保持，但最终被改回去了（应用侧多恢复了，例如按容器整个放回） |
| 连带变化 side_effects | AI 没直接改，但最终变了 |
| 来源不明 unattributed | 说不准是谁做的（第 5.4、5.5 节）：按人的修改保护 |

违规的照实记下（作者是这个 AI，标违规），单元仍然归人；提醒人；暂停这个 AI（默认），人看过再让它继续（马上落盘）。开许可单之后规则状态又变了的（例如人的修改是事后才记的）同样记为违规。

**结局**：`committed`（没有违规，可能部分生效）、`refused`（准入或预检查就拒，没有执行）、`replan`（场景已变，没有执行，重开许可单再试）、`deferred`（人正在改，延后）、`error`（AI 的代码出错，已生效的照实记）、`breach`（有违规）、`unknown`（结果没收到）。**成功** = 没有违规，并且账本和实际一致。

### 5.4 不能原子执行的执行

执行期间人也可能在改（一条命令跑了两分钟，人接着打字；一次工具调用在执行前、执行后两次通知之间）。结束之后，每个容器的变化（`rules.settle_window`）：

- 很快就结束了（不超过 3 秒，`RIGHTOFWAY_BASH_WINDOW` 可以改），或者变化之后正好是一个已知的参照（git 的 HEAD、暂存区：多半是命令做的），或者删掉了有不能改的单元的容器：算这个 AI 的；碰到了不能改的单元就放回整个容器，AI 的版本另存一份；
- 其余的（执行了比较久，内容又不是参照里的）：说不准是谁的，记为来源不明、按人的修改保护；**不放回**（放回可能抹掉人刚做的修改），碰到了人的部分时把改动之前的样子另存一份，提醒人；
- 没等到结束通知：变化一律说不准是谁的；
- 只有人能改的容器：碰到了就放回，不管多久。

事先算出了结果的执行（第 5.2 节），结束后实际和算的不一样：算出来的那部分是 AI 的，多出来的说不准是谁的（`rules.settle_predicted`）。

### 5.5 结果没收到

发出去了、结果没收到，可能执行了，也可能没有。按应用侧记的日志查清（`rules.resolve_lost`）：

- 查回来了（应用记了完成）→ 照常结算，AI 的改动算 AI 的；
- 不能原子执行的工具调用开始了、还没收尾，应用没重新打开过 → 很快就查到的，补做收尾再结算；开始之后过了很久的，这期间的变化说不准是谁的（第 5.4 节），不补做收尾，按人的修改保护；
- 只有两种情况能说"没执行"：应用记了"没执行"；或者应用执行前就记"开始了"，而这次启动以来根本没收到过这张许可单；
- 其余的（开始了、没交回结果；应用重开过；应用不记结果）：查不回来，和执行前不一样的地方记为来源不明、按人的修改保护，提醒人；确知执行了时，许可单里要保持、现在又不一样的部分可能是 AI 改了、没恢复成：当作可能的违规，提醒人、暂停这个 AI（`rules.suspects`）。

查清之后，那个 AI 下一次调用时先收到说明。

## 6 说明和不变量

**说明**只从账本生成（P9）。核心产出结构化的事实（`core/explain.py`）：哪些单元没生效、谁的、为什么、现在的值和 AI 想改成的值；失效的事实和新的目标（"以现在的值为准"）；部分生效的对象；派生的改动（AI 新建的是副本、人改过的共用数据少了使用者）；要给人的按钮（允许重建、不是同一个，每件事只提醒一次）；同一个单元被拦了几次（`core/loops.py`：到 3 次提醒人一次，这是告知，不是保护手段）。写成媒介的说法、带上名字和值，由各媒介的说明模块做（`code/messages.py`、`blender/messages.py`），名字和值由应用侧给。

**三条不变量**（`core/invariants.py`），测试和实验的每一步都查：

1. **账本 = 实际**：账本里每个单元的指纹和应用里实际的一致；没建记录的基线单元按基线比，一样要一致（不因为只记有作者的单元而放宽）；
2. **保持的就是保持的**：要保持的单元执行后要么没变，要么记成了违规；
3. **说的都是真的**：说"已生效"的，实际就是 AI 改成的样子；说"没生效、保留了原来的"，实际和账本里都还是原来的样子。

## 7 账本和存盘

账本只记有作者的单元（第 2 节），以及墓碑、每个 AI 看过的版本、还没结算的许可单、要告诉 AI 的话。存盘是追加写的日志（`core/store.py`）：第一行是整份记录（快照），之后每一步只追加这一步的变化；日志长了（行数、字节数超过上限，或者比快照还大）就整份重写一次，先写临时文件再 `os.replace`；最后一行没写完（存到一半退出）就读到它前面为止。很大、只在压缩时才需要重写的部分（例如 3D 的观察缓存）可以是快照的附属文件。几个进程同时用同一个账本时（例如几个 hook 一起跑）加文件锁。

## 8 两侧接口

两侧互相独立（`core/interfaces.py`），任何一个 AI 侧都能配任何一个应用侧：

- **AI 侧**（在哪里截住 AI）：交给核心"AI 想做什么"（`Intent`：一次编辑、一条命令、一次工具调用、一段代码）和"做完了"；拿回放行还是拒绝、要对 AI 说的话、要提醒人的话。它只和 `Session` 说话：`intro`（会话开始）、`prompt`（人发了消息，可能带交还）、`begin`（执行前）、`end`（执行后）、`look`（AI 读了东西）。现有：Claude Code 的 hooks（`code/hooks.py`）、MCP 代理（`proxy/`）。
- **应用侧**（东西存在哪、怎么看见、怎么放回）：交给核心单元和指纹、名字和值、身份跟踪（认回的配对，或者位置的对应关系）、能力；拿回这次要保持哪些单元、要清掉哪些重建出来的东西。现有：文本文件（`code/ledger.py`、`code/lines.py`；`code/session.py` 是它对 AI 侧的那一层）、Blender（`blender/blender_side.py`、`bridge.py`，`shared_session.py` 里观察的部分；`blender/hook_session.py` 让执行前后各通知一次的 AI 侧也能驱动它）、Unity、模拟应用（`fakeapp.py`）。

**能力**不手写，靠自测得出（P4）：

| 能力 | 意思 |
|---|---|
| predict | 执行前就能算出结果 |
| atomic | 能把"快照 → 执行 → 放回"包成一次做完 |
| around | 能把一次不透明的工具调用包在快照和放回之间 |
| restore / restore_deleted | 能放回改掉的单元 / 删掉的东西 |
| identity | 能认出删了又建的是同一个东西 |
| journal | 按许可单编号记执行结果 |
| editing | 能看见人正在改哪里 |

组合起来能有多强的保证，取决于两侧各自的能力，核心按报上来的能力决定怎么处理（第 5.2、5.4 节），做不到的照实说（P1）。

## 9 早期的操作模型

`runtime.py` 里还留着 v0.2–v0.4 的逐项提交模型：`submit` / `complete`（操作带着读集、写集的基准版本）、步骤（认领、分配给人、失效传播、撤回）、"留作候选"和"合并"两种策略、副作用等级 3 要人确认、暂停时排队和暂存结果、外部修改、权威副本。它建在核心上（`Runtime` 继承 `KeyedLedger`），和许可单共用总闸、暂时不能改的情况和"归人"，但按 R4 严格比较基准版本：基准版本不是当前版本就算过时，不管是谁改的。还在用它的：实时同步（`blender/live_sync.py`）、文件兜底（`blender/filemerge.py`）、对照组的记账、集合增减（`membership.py`）和旧场景的测试。新代码用许可单。

## 10 一致性测试

给写适配的人用：照 `rightofway/conformance.py` 的 `Driver` 实现几个动作（初始内容、人改一下、人删一下、人交还、AI 改、AI 删、AI 建、AI 看、结果没收到、查清、读实际的值、查不变量、报能力），跑一遍就知道有没有守住保证：

```
python -m rightofway.conformance        对能跑的应用侧都跑一遍，打印能力报告，写进 experiments/results/conformance.json
python -m pytest tests/test_core.py     同样的场景和随机差分测试，作为测试
```

- **场景**（和媒介无关）：人改了、AI 再改同一处；AI 改别处；人删了、AI 又建回来；AI 删人改过的东西；结果没收到（期间人改了别处）；交还之后；两个 AI。每一步都查三条不变量。
- **三档**：保护住了（protected）；保护不住，但如实报告了（reported：记违规、提醒人、暂停 AI）；说了假话（lied：账本和实际对不上，说"已生效""已恢复"其实没有，或者人的修改丢了却没人知道）。只有这一档不及格。
- **能力报告**：每个应用侧的能力（第 8 节）和每个场景的结果。
- **随机的差分测试**：同一串随机操作（人改、AI 改、AI 看、人交还），应用侧的结果和一个独立写的判断表模型逐步对照，每一步查不变量。
- **现有的应用侧**：模拟应用、恢复不了删除的模拟应用（和现在的 Unity 一样）、文本文件（经由 Claude Code 的 hooks）、单元是字符的玩具容器（只在测试里用，证明核心不认识"行"）、Blender（有 bpy 时），以及一个跨组合：Claude Code 的 hooks 驱动按编号的模拟应用。

## 11 规则在哪

## 12 还没做的、做不到的

- **3D 的墓碑只认人（或来源不明）删掉的**：别的 AI 删掉的对象，按名字认回容易认错（删掉一个 AI 正常新建的对象），所以按编号的容器不对它立墓碑；表里"别的 AI 删的，先看过这次删除"这一格，现在只有按位置的容器做到了。
- **3D 正常结束、但执行得比较久的工具调用**（MCP 代理转发的类型化工具）：调用期间的变化仍然都算 AI 的；第 5.4 节的规则在这条路上只用在了结果没收到、过了很久才查到的情况，以及 hooks 这种执行前后各通知一次的 AI 侧。要用上，接入代码的收尾得能"只交回实际状态、不放回"。
- hooks 驱动 3D 应用时，执行前后之间的票据记在内存里：真的 Claude Code 每个 hook 事件是一个新进程，要从账本接着用，没结算的那次由结果未知的记录查清。
- 账本文件坏了（不是最后一行没写完）时，两边都当作没有账本，从头开始；更安全的做法是不放行、请人处理。
- 早期的操作模型仍然按 R4 严格比较基准版本（第 9 节），和判断表在"交还之后、AI 还没看过"这一格上不一样。
